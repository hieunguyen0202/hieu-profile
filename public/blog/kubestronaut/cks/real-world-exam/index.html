    CKS Real World exam — Questions and Answers

    Thirteen hands-on tasks. Read the question, solve it against kubernetes.io/docs, then check the answer.

    Tasks: 13 Pace: ~7–8 minutes each Lab: your cluster only

    Time strategy

    • Real exam: roughly 15–16 items, 120 minutes. Budget ~7 minutes; some items need 15+.
    • Triage in one minute: score it now, or flag and skip.
    • Control-plane YAML: keep a working kubeconfig before you bounce static pods.
    • “Do not add or remove” means one-line / one-field edits only.

    Task 1 — CIS: worker kubelet and etcd

    Question

    Docs: kubelet configuration, etcd, kubeadm static pods

    Scenario: A CIS-style scan of this kubeadm node reports two worker issues and one datastore issue. You may use crictl or docker depending on the runtime.

    Goal: Persist the fixes in config (not one-off CLI flags that vanish on reboot) and bounce only the components you change.

    Worker agent

    • Unauthenticated kubelet requests must be rejected.
    • Authorization must not be “allow everything”. Prefer webhook mode so kubelet asks the API server.

    Datastore

    • Clients talking to etcd must present a certificate (client-cert-auth on).

    Answer

    Kubelet — /var/lib/kubelet/config.yaml:

    authentication:
  anonymous:
    enabled: false
  webhook:
    enabled: true
authorization:
  mode: Webhook
    sudo systemctl restart kubelet
sudo systemctl status kubelet

    Bad indent → kubelet crash. Watch journalctl -u kubelet -f.

    etcd — command in /etc/kubernetes/manifests/etcd.yaml:

    - --client-cert-auth=true

    Static-pod restart is automatic. Sanity check:

    sudo crictl ps | grep etcd
kubectl get nodes
kubectl get pods -n kube-system

    NotReady after webhook auth often means kubelet cannot call the API — check kubelet kubeconfig, not only etcd.

    Task 2 — Lock down the API server

    Question

    Docs: kube-apiserver flags, RBAC, admission plugins

    Scenario: This lab cluster was opened up for debugging. Unauthenticated clients can still talk to the API, and admission is too loose for nodes.

    Goal

    1. Turn anonymous authentication off.
    2. Authorize with Node then RBAC (that order).
    3. Ensure the NodeRestriction admission plugin is enabled (keep existing plugins).
    4. Remove the cluster-wide binding that grants the anonymous identity extra rights (name is typically system:anonymous — confirm with kubectl get clusterrolebinding before delete).

    Constraint: After the API hardens, a kubeconfig that relied on anonymous access will fail. Switch to the kubeadm admin file on the control plane, usually /etc/kubernetes/admin.conf.

    Answer

    sudo vi /etc/kubernetes/manifests/kube-apiserver.yaml
    - --anonymous-auth=false
- --authorization-mode=Node,RBAC
- --enable-admission-plugins=...,NodeRestriction

    Missing --anonymous-auth means the default (true). Append NodeRestriction; do not drop ServiceAccount or other plugins already listed.

    export KUBECONFIG=/etc/kubernetes/admin.conf
kubectl get nodes
kubectl delete clusterrolebinding system:anonymous
kubectl get clusterrolebinding | grep anonymous

    Task 3 — Image admission webhook

    Question

    Docs: ImagePolicyWebhook, AdmissionConfiguration

    Scenario: Security wants every new Pod image reviewed by an HTTPS scanner before it is admitted. A half-finished drop-in already exists on the control plane under /etc/kubernetes/image-gate/ (AdmissionConfiguration + kubeconfig). The scanner URL to use is https://img-review.lab.internal/v1/check.

    Goal

    1. Turn on the admission plugin that matches that config, and point the API server at the AdmissionConfiguration file.
    2. Fail closed: if the scanner is down or times out, reject the image.
    3. Set the kubeconfig cluster server to the URL above.
    4. Apply the sample workload at /opt/cks-lab/bad-image.yaml (it should be denied). Recreate if you need another attempt.

    Scanner access log (if nginx is the front): /var/log/nginx/access.log.

    Answer

    API server flags + hostPath for /etc/kubernetes/image-gate if it is not mounted:

    - --enable-admission-plugins=NodeRestriction,ImagePolicyWebhook
- --admission-control-config-file=/etc/kubernetes/image-gate/admission_configuration.yaml

    Fail closed:

    apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
- name: ImagePolicyWebhook
  configuration:
    imagePolicy:
      kubeConfigFile: /etc/kubernetes/image-gate/kubeconfig.yaml
      allowTTL: 50
      denyTTL: 50
      retryBackoff: 500
      defaultAllow: false
    server: https://img-review.lab.internal/v1/check
    kubectl apply -f /opt/cks-lab/bad-image.yaml
sudo crictl logs $(sudo crictl ps -a --name kube-apiserver -q)
sudo tail -f /var/log/nginx/access.log

    You want an ImagePolicyWebhook deny. Silent access log usually means the plugin never called the backend (flag, mount, or kubeconfig path).

    Task 4 — One-line image + one-field workload

    Question

    Docs: Dockerfile best practices, Pod securityContext

    Scenario: Files for a small app sit in /opt/cks-lab/hardened-build/.

    Goal

    • In build/Dockerfile, change exactly one existing instruction so it is safer. Do not insert or delete lines. Do not docker build (image size / scoring).
    • In app-deploy.yaml, change exactly one existing field. Do not add or remove keys.

    If the lab needs a non-root user and no named account is required, use numeric UID 65535 (nobody on many distros).

    Answer

    Dockerfile — most common one-instruction fix:

    USER 65535

    Alternatives if that line is already correct: drop a plaintext ENV secret, or replace ADD with COPY — still only one instruction.

    Deployment — most common one-field fix:

    securityContext:
  runAsUser: 65535

    Or a boolean already present: privileged / allowPrivilegeEscalation flipped to false. Apply only if the prompt asks you to roll the workload out.

    Task 5 — Contain a host-memory reader

    Question

    Scenario: Runtime telemetry shows a process inside a Kubernetes Pod has an open file descriptor on /dev/mem (physical memory). Container runtime on the node may be Docker or containerd.

    Goal: Identify that Pod, then stop it by scaling its controller Deployment to 0 replicas.

    Constraints: Do not patch the Pod template, do not delete the Deployment, do not touch unrelated Deployments.

    Answer

    docker ps   # or: sudo crictl ps
for cid in $(docker ps -q); do
  echo "=== $cid ==="
  pids=$(docker top "$cid" -eo pid | tail -n +2)
  for pid in $pids; do
    ls -l /proc/$pid/fd 2>/dev/null | grep -i mem && echo "FOUND $cid pid $pid"
  done
done
    docker inspect <container_id> | grep -iE "io.kubernetes.pod.name|io.kubernetes.pod.namespace"
kubectl get pod <pod> -n <ns> -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'
kubectl scale deployment <deploy> -n <ns> --replicas=0

    ReplicaSet → Deployment: follow ownerReferences. Containment is scale-to-zero, not kubectl delete.

    Task 6 — Immutable, non-root workload

    Question

    Docs: Pod securityContext

    Scenario: Namespace webstack runs Deployment cms. A starter manifest is at /opt/cks-lab/webstack/cms.yaml.

    Goal: Every container in that Deployment must:

    • run as UID 20000
    • have a read-only root filesystem
    • not be allowed to escalate privileges

    Apply the change so new Pods pick it up.

    Answer

    securityContext:
  runAsUser: 20000
  readOnlyRootFilesystem: true
  allowPrivilegeEscalation: false
    kubectl apply -f /opt/cks-lab/webstack/cms.yaml
kubectl rollout status deployment/cms -n webstack

    CrashLoop because the app writes to the container root is common. Extra emptyDir for /tmp only if the prompt allows extra fields.

    Task 7 — Opt-in ServiceAccount token

    Question

    Docs: ServiceAccount automount, projected serviceAccountToken

    Scenario: In namespace observe, ServiceAccount metrics-agent-sa currently gets the default API token in every Pod. Deployment metrics-agent still needs a token, but only as an explicit volume.

    Goal

    • Disable automount on the ServiceAccount.
    • On the Deployment, add a projected volume named token, mount it read-only so the file appears at the usual path /var/run/secrets/kubernetes.io/serviceaccount/token.

    Answer

    kubectl patch serviceaccount metrics-agent-sa -n observe \
  -p '{"automountServiceAccountToken": false}'
    spec:
  template:
    spec:
      serviceAccountName: metrics-agent-sa
      containers:
      - name: metrics-agent
        volumeMounts:
        - name: token
          mountPath: /var/run/secrets/kubernetes.io/serviceaccount
          readOnly: true
      volumes:
      - name: token
        projected:
          sources:
          - serviceAccountToken:
              path: token
              expirationSeconds: 3607
    kubectl rollout status deployment/metrics-agent -n observe
kubectl exec -n observe deploy/metrics-agent -- ls /var/run/secrets/kubernetes.io/serviceaccount/

    Task 8 — Package version and SPDX

    Question

    Scenario: Namespace base-images, Deployment apk-trio: three containers, three different Alpine tags.

    Goal: Find which image has apk package libcrypto3 at version 3.1.4-r5. Generate an SPDX SBOM for that image with the preinstalled bom CLI and write it to /opt/cks-lab/apk-trio.spdx.

    Answer

    kubectl get deployment apk-trio -n base-images -o jsonpath='{range .spec.template.spec.containers[*]}{.name}{"  "}{.image}{"\n"}{end}'
kubectl exec -n base-images <pod> -c <c1> -- apk list --installed | grep libcrypto3
kubectl exec -n base-images <pod> -c <c2> -- apk list --installed | grep libcrypto3
kubectl exec -n base-images <pod> -c <c3> -- apk list --installed | grep libcrypto3
    bom generate --image=<matching-image> --output=/opt/cks-lab/apk-trio.spdx
grep -A2 -i libcrypto3 /opt/cks-lab/apk-trio.spdx
# bom generate --help if flags differ

    Task 9 — Engine socket and group

    Question

    Docs: dockerd daemon.json, systemd drop-ins

    Scenario: Host user intern can talk to the Docker socket because they are in group docker. The daemon may also be listening on TCP.

    Goal

    • Drop intern from group docker only (leave other groups alone).
    • Unix socket ownership/group should be root.
    • No TCP listen for dockerd.

    Kubernetes on this node must still schedule after the restart.

    Answer

    sudo gpasswd -d intern docker
groups intern
    {
  "group": "root",
  "hosts": ["unix:///var/run/docker.sock"]
}

    Strip -H tcp://... from systemd ExecStart if present, then:

    sudo systemctl daemon-reload
sudo systemctl restart docker
sudo ss -tlnp | grep dockerd
kubectl get nodes
kubectl get pods -A | grep -v Running

    Task 10 — TLS Secret the app already mounts

    Question

    Docs: kubectl create secret tls

    Scenario: Namespace shop, Deployment storefront already volume-mounts a Secret named shop-tls. The PEM files are on disk:

    • /opt/cks-lab/shop/storefront.example.crt
    • /opt/cks-lab/shop/storefront.example.key

    Goal: Create that TLS Secret so the existing mount starts working. Do not rewrite the Deployment unless it is broken for another reason.

    Answer

    kubectl create secret tls shop-tls \
  -n shop \
  --cert=/opt/cks-lab/shop/storefront.example.crt \
  --key=/opt/cks-lab/shop/storefront.example.key
kubectl get secret shop-tls -n shop -o yaml
kubectl get pods -n shop

    Type kubernetes.io/tls; keys tls.crt / tls.key.

    Task 11 — API audit trail

    Question

    Docs: Kubernetes audit policy and apiserver audit flags

    Scenario: Audit is not wired. A starter policy that mostly says “do not log X” lives at /etc/kubernetes/audit/policy.yaml. You must attach it to kube-apiserver and expand the rules.

    Runtime flags to set

    • Policy: /etc/kubernetes/audit/policy.yaml
    • Log file: /var/log/k8s/audit.json
    • Keep at most 2 rotated files; keep files 10 days

    Policy additions (first-match; keep the existing omit rules)

    • Namespace objects: request + response bodies.
    • Deployments in namespace storefront: request body only.
    • ConfigMaps and Secrets (all namespaces): metadata only.
    • Everything else: metadata only.

    Mount host paths for the policy directory and the log directory into the apiserver static pod.

    Answer

    - --audit-policy-file=/etc/kubernetes/audit/policy.yaml
- --audit-log-path=/var/log/k8s/audit.json
- --audit-log-maxbackup=2
- --audit-log-maxage=10

    Specific rules above existing level: None. Catch-all Metadata last.

    apiVersion: audit.k8s.io/v1
kind: Policy
rules:
- level: RequestResponse
  resources:
  - group: ""
    resources: ["namespaces"]
- level: Request
  namespaces: ["storefront"]
  resources:
  - group: "apps"
    resources: ["deployments"]
- level: Metadata
  resources:
  - group: ""
    resources: ["configmaps", "secrets"]
# existing level: None rules
- level: Metadata

    Request = request body; RequestResponse = both. Namespace is cluster-scoped — do not put it under a namespace filter.

    Task 12 — Default-deny plus one allow

    Question

    Docs: NetworkPolicy, namespaceSelector

    Scenario: Namespace frontend is labeled tier=frontend. Namespace backend is labeled tier=backend. Workloads already exist; leave them alone.

    Goal

    • In frontend, create NetworkPolicy drop-ingress that selects all Pods and denies all ingress.
    • In backend, create NetworkPolicy from-frontend that selects all Pods and allows ingress only from Pods whose namespace has tier=frontend.

    Create only NetworkPolicies. Do not relabel namespaces or edit Pods.

    Answer

    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: drop-ingress
  namespace: frontend
spec:
  podSelector: {}
  policyTypes:
  - Ingress
    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: from-frontend
  namespace: backend
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          tier: frontend
    kubectl apply -f drop-ingress.yaml
kubectl apply -f from-frontend.yaml

    Task 13 — Cilium Ingress with TLS

    Question

    Scenario: Cilium is the default IngressClass. Namespace shop already has Service catalog and TLS Secret catalog-cert.

    Goal: Create Ingress catalog so that:

    • Host catalog.lab.internal, path prefix /, backend Service catalog port 80
    • TLS terminates with Secret catalog-cert
    • Plain HTTP is redirected to HTTPS

    Answer

    apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: catalog
  namespace: shop
spec:
  ingressClassName: cilium
  tls:
  - hosts:
    - catalog.lab.internal
    secretName: catalog-cert
  rules:
  - host: catalog.lab.internal
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: catalog
            port:
              number: 80

    If HTTP still answers without redirect:

    metadata:
  annotations:
    ingress.cilium.io/force-https: "true"
    kubectl apply -f catalog-ingress.yaml
curl -L http://catalog.lab.internal

    TLS host list must match rules.host exactly.
