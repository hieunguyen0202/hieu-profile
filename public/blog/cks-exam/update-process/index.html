    Kubernetes Update Process

    Before proceeding with the update process, let's review Kubernetes releases.

    Why is it necessary to upgrade Kubernetes frequently?

    • Support
    • Security fixes
    • Bug fixes
    • Keep dependencies updated (CVEs)

    Keeping Kubernetes updated is an ongoing task that should always be performed from time to time.

    Always stay updated on the patch version of your minor release. The patch is usually released at least once a month, but depending on the severity of the fix, it may be released earlier.

    Sequence:

    1. Upgrade master components: apiserver, controller-manager, scheduler, kubelet when present.

      • 1.1 kubectl drain: to remove pods from the node and prevent them from being scheduled again. Drain automatically performs cordon, so we are only responsible for uncordon.
      • 1.2 Upgrade
      • 1.3 kubectl uncordon: release the node so it can receive pods again.

    2. Upgrade worker components: kubelet, kube-proxy. Same sequence as master, but for different components.

    3. Components must be on the same version (minor) as the apiserver, not necessarily the same patch, but it's recommended. Up to one version below is supported.

    How to make applications survive an upgrade?

    • Pod gracePeriod/ Terminating state
    • Pod Lifecycle events
    • Pod DisruptionBudget

    Answering the question above...

    This happens because the pods app1 and app2 in the default namespace are not managed by a controller (like a Deployment, StatefulSet, etc.), which means they don't have an automatic mechanism to be recreated. When you try to drain the node, Kubernetes avoids deleting these pods to avoid disrupting critical applications that cannot be easily recreated.

    The kubectl drain command is being stopped because it tries to avoid accidentally deleting uncontrolled pods. To force the deletion of these pods and continue the drain process, you can add the --force flag to the command:

    kubectl drain cks-worker --ignore-daemonsets --delete-emptydir-data --force

    Use this option carefully, as deleted pods will not be recreated automatically. If these pods are important and cannot be lost, it's better to check why they don't have a controller and consider adding an appropriate controller.

    A pod without a controller will not return, so always have a pod with deployment or some other controller.
