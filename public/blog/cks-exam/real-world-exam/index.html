    CKS Real World exam — Questions and Answers

    Thirteen hands-on tasks. Read the question, solve it against kubernetes.io/docs, then check the answer.

    Tasks: 13 Pace: ~7–8 minutes each Lab: your cluster only

    Time strategy

    • About 16 items in 2 hours. Some tasks take 15–20 minutes.
    • In 60 seconds decide: quick win or time sink. Bookmark sinks and collect easy points first.
    • API server / etcd static-pod edits: leave disruptive restarts until you have a working kubeconfig (/etc/kubernetes/admin.conf).
    • If the prompt says “do not add or remove instructions/fields”, change exactly one value.

    Task 1 — CIS: kubelet and etcd

    Question

    Docs: kubeadm, kubelet, etcd

    Context: Fix CIS Benchmark findings on a kubeadm cluster.

    Task: Fix via configuration and restart affected components.

    Kubelet (Docker Engine may be the runtime — use docker if you need to inspect containers):

    • anonymous-auth must be false — FAIL
    • --authorization-mode must not be AlwaysAllow — FAIL

    Use Webhook authentication/authorization where possible.

    etcd:

    • --client-cert-auth must be true — FAIL

    Answer

    Kubelet — edit /var/lib/kubelet/config.yaml:

    authentication:
  anonymous:
    enabled: false
  webhook:
    enabled: true
authorization:
  mode: Webhook
    sudo systemctl restart kubelet
sudo systemctl status kubelet

    If kubelet fails, check YAML indent: journalctl -u kubelet -f.

    etcd — static pod /etc/kubernetes/manifests/etcd.yaml, under command:

    - --client-cert-auth=true

    Kubelet restarts the static pod. Confirm:

    sudo crictl ps | grep etcd
kubectl get nodes
kubectl get pods -n kube-system

    If the node goes NotReady, the kubelet webhook cannot reach the API server — fix kubelet kubeconfig / webhook settings.

    Task 2 — API server: anonymous auth, Node,RBAC, NodeRestriction

    Question

    Docs: kubeadm, ClusterRoleBinding, kubectl

    Context: For testing, the kubeadm API server allows unauthenticated and unauthorized access.

    Task:

    • Forbid anonymous authentication
    • Authorization mode Node,RBAC
    • Admission plugin NodeRestriction

    Docker Engine may be the runtime. Current kubectl uses unauthenticated access — it will stop working after you lock the API. Use /etc/kubernetes/admin.conf afterwards.

    Then delete ClusterRoleBinding system:anonymous.

    Answer

    sudo vi /etc/kubernetes/manifests/kube-apiserver.yaml
    - --anonymous-auth=false
- --authorization-mode=Node,RBAC
- --enable-admission-plugins=...,NodeRestriction

    If --anonymous-auth is missing, default is true — add the flag. Append NodeRestriction; do not wipe other plugins (e.g. ServiceAccount).

    export KUBECONFIG=/etc/kubernetes/admin.conf
kubectl get nodes
kubectl delete clusterrolebinding system:anonymous
kubectl get clusterrolebinding | grep anonymous

    Task 3 — ImagePolicyWebhook

    Question

    Docs: Admission Controllers, Deployments

    Context: Wire a container image scanner into kubeadm.

    Incomplete config lives under /etc/kubernetes/bouncer. Scanner HTTPS endpoint: https://smooth-yak.local/review.

    1. Enable admission plugin(s) needed for the given AdmissionConfiguration.
    2. Deny images when the backend fails (fail closed).
    3. Point the webhook backend at https://smooth-yak.local/review.
    4. Deploy /home/candidate/vulnerable.yaml (image that must be denied). Recreate as needed.

    Scanner log: /var/log/nginx/access_log.

    Answer

    On kube-apiserver.yaml:

    - --enable-admission-plugins=NodeRestriction,ImagePolicyWebhook
- --admission-control-config-file=/etc/kubernetes/bouncer/admission_configuration.yaml

    Mount hostPath /etc/kubernetes/bouncer into the apiserver pod if it is not already mounted.

    admission_configuration.yaml — fail closed:

    apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
- name: ImagePolicyWebhook
  configuration:
    imagePolicy:
      kubeConfigFile: /etc/kubernetes/bouncer/kubeconfig.yaml
      allowTTL: 50
      denyTTL: 50
      retryBackoff: 500
      defaultAllow: false

    kubeconfig.yaml cluster server:

    server: https://smooth-yak.local/review
    kubectl apply -f /home/candidate/vulnerable.yaml
sudo crictl logs $(sudo crictl ps -a --name kube-apiserver -q)
sudo tail -f /var/log/nginx/access_log

    Expect an ImagePolicyWebhook deny. No new access-log line means the plugin is not calling the scanner.

    Task 4 — Dockerfile and Deployment (one change each)

    Question

    Docs: Deployments, Pods

    Edit /home/candidate/subtle-bee/build/Dockerfile: fix one existing instruction (security/best-practice). Do not add or remove instructions. Do not build the image (storage / score).

    Edit /home/candidate/subtle-bee/deployment.yaml: fix one existing field. Do not add or remove fields.

    If you need an unprivileged user: nobody, UID 65535.

    Answer

    Dockerfile — typical fix (numeric UID, does not depend on /etc/passwd):

    USER 65535

    Other one-line issues: hardcoded ENV secret, or ADD where COPY is safer. Change only that line.

    Deployment — typical securityContext fix:

    securityContext:
  runAsUser: 65535

    Or flip privileged: true → false, or allowPrivilegeEscalation: true → false. Only one field. Apply only if the prompt requires it.

    Task 5 — Pod reading /dev/mem

    Question

    Context: A Pod is a security threat.

    One Pod of application ollama reads /dev/mem. Identify it. Runtime may be Docker. Then find the managing Deployment and scale it to zero.

    Do not change the Deployment except replicas. Do not modify or delete other Deployments.

    Answer

    docker ps
for cid in $(docker ps -q); do
  echo "=== $cid ==="
  pids=$(docker top "$cid" -eo pid | tail -n +2)
  for pid in $pids; do
    ls -l /proc/$pid/fd 2>/dev/null | grep -i mem && echo "FOUND $cid pid $pid"
  done
done
    docker inspect <container_id> | grep -iE "io.kubernetes.pod.name|io.kubernetes.pod.namespace"
kubectl get pod <pod> -n <ns> -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'
kubectl scale deployment <deploy> -n <ns> --replicas=0

    Do not edit the spec or delete the Deployment. Contain first.

    Task 6 — Immutable containers on lamp-deployment

    Question

    Docs: Deployment, Pod, Namespace

    Update Deployment lamp-deployment in namespace lamp so containers:

    • run as UID 20000
    • use a read-only root filesystem
    • forbid privilege escalation

    Manifest: /home/candidate/finer-sunbeam/lamp-deployment.yaml.

    Answer

    Under each container:

    securityContext:
  runAsUser: 20000
  readOnlyRootFilesystem: true
  allowPrivilegeEscalation: false
    kubectl apply -f /home/candidate/finer-sunbeam/lamp-deployment.yaml
kubectl rollout status deployment/lamp-deployment -n lamp

    If the app crashes on writes to /tmp, that is expected without extra emptyDir — only add volumes if the prompt allows. On the exam, add only the three fields unless Pods stay CrashLoop.

    Task 7 — ServiceAccount token automount

    Question

    Docs: ServiceAccount, Deployment, Projected Volumes

    SA stats-monitor-sa in monitoring: turn off automount of API credentials.

    Deployment stats-monitor in monitoring: inject a token at /var/run/secrets/kubernetes.io/serviceaccount/token using a Projected Volume named token, mounted read-only.

    Answer

    kubectl patch serviceaccount stats-monitor-sa -n monitoring \
  -p '{"automountServiceAccountToken": false}'
    spec:
  template:
    spec:
      serviceAccountName: stats-monitor-sa
      containers:
      - name: stats-monitor
        volumeMounts:
        - name: token
          mountPath: /var/run/secrets/kubernetes.io/serviceaccount
          readOnly: true
      volumes:
      - name: token
        projected:
          sources:
          - serviceAccountToken:
              path: token
              expirationSeconds: 3607
    kubectl rollout status deployment/stats-monitor -n monitoring
kubectl exec -n monitoring deploy/stats-monitor -- ls /var/run/secrets/kubernetes.io/serviceaccount/

    Task 8 — libcrypto3 version + SPDX SBOM

    Question

    Deployment alpine in namespace alpine has three containers with different alpine images.

    Find which image has package libcrypto3 version 3.1.4-r5.

    Use pre-installed bom to write an SPDX document to /home/candidate/alpine.spdx.

    Answer

    kubectl get deployment alpine -n alpine -o jsonpath='{range .spec.template.spec.containers[*]}{.name}{"  "}{.image}{"\n"}{end}'
kubectl get pod -n alpine -l app=alpine  # adjust label
kubectl exec -n alpine <pod> -c <c1> -- apk list --installed | grep libcrypto3
kubectl exec -n alpine <pod> -c <c2> -- apk list --installed | grep libcrypto3
kubectl exec -n alpine <pod> -c <c3> -- apk list --installed | grep libcrypto3
    bom generate --image=<matching-image> --output=/home/candidate/alpine.spdx
grep -A2 -i libcrypto3 /home/candidate/alpine.spdx
# bom generate --help if flags differ

    Task 9 — Harden Docker daemon

    Question

    Docs: dockerd

    • Remove user developer from group docker only (keep other groups).
    • Unix socket group must be root.
    • Docker must not listen on any TCP port.

    Cluster must stay healthy afterwards.

    Answer

    sudo gpasswd -d developer docker
groups developer
    {
  "group": "root",
  "hosts": ["unix:///var/run/docker.sock"]
}

    If systemd ExecStart has -H tcp://..., remove it (systemctl edit docker --full or drop-in). Then:

    sudo systemctl daemon-reload
sudo systemctl restart docker
sudo ss -tlnp | grep dockerd
kubectl get nodes
kubectl get pods -A | grep -v Running

    Task 10 — TLS Secret for existing Deployment

    Question

    Docs: Secrets, TLS Secrets, Volumes

    Create TLS Secret clever-cactus in namespace clever-cactus for Deployment clever-cactus.

    • Cert: /home/candidate/clever-cactus/web.k8s.local.crt
    • Key: /home/candidate/clever-cactus/web.k8s.local.key

    The Deployment already mounts the Secret.

    Answer

    kubectl create secret tls clever-cactus \
  -n clever-cactus \
  --cert=/home/candidate/clever-cactus/web.k8s.local.crt \
  --key=/home/candidate/clever-cactus/web.k8s.local.key
kubectl get secret clever-cactus -n clever-cactus -o yaml
kubectl get pods -n clever-cactus

    Type must be kubernetes.io/tls with keys tls.crt and tls.key.

    Task 11 — Audit policy

    Question

    Docs: Auditing

    Reconfigure the API server:

    • Policy file: /etc/kubernetes/logpolicy/audit-policy.yaml
    • Log path: /var/log/kubernetes/audit-logs.txt
    • Max 2 backup logs, retain 10 days

    The basic policy only lists what not to log. Extend it to log:

    • namespaces at RequestResponse
    • request body of deployments in namespace webapps
    • ConfigMap and Secret in all namespaces at Metadata
    • all other requests at Metadata

    The API server must use the extended policy.

    Answer

    Flags on kube-apiserver + hostPath mounts for policy dir and log dir:

    - --audit-policy-file=/etc/kubernetes/logpolicy/audit-policy.yaml
- --audit-log-path=/var/log/kubernetes/audit-logs.txt
- --audit-log-maxbackup=2
- --audit-log-maxage=10

    Rules are first-match. Put specific rules above existing level: None. Catch-all Metadata at the bottom.

    apiVersion: audit.k8s.io/v1
kind: Policy
rules:
- level: RequestResponse
  resources:
  - group: ""
    resources: ["namespaces"]
- level: Request
  namespaces: ["webapps"]
  resources:
  - group: "apps"
    resources: ["deployments"]
- level: Metadata
  resources:
  - group: ""
    resources: ["configmaps", "secrets"]
# keep existing level: None rules here
- level: Metadata

    Request = request body only; RequestResponse = request + response. Namespaces are cluster-scoped (no namespace filter).

    Task 12 — NetworkPolicies

    Question

    Docs: Namespace, NetworkPolicy, Pod

    Create deny-policy in namespace prod (label env:prod) blocking all ingress.

    Create allow-from-prod in namespace data (label env:data) allowing ingress only from Pods in prod, using the namespace label.

    Do not modify or delete namespaces or Pods. Only create the NetworkPolicies.

    Answer

    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-policy
  namespace: prod
spec:
  podSelector: {}
  policyTypes:
  - Ingress
    apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-prod
  namespace: data
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          env: prod
    kubectl apply -f deny-policy.yaml
kubectl apply -f allow-from-prod.yaml

    Task 13 — Cilium Ingress, TLS, HTTP→HTTPS

    Question

    Default Cilium IngressClass is configured. Create Ingress web in namespace prod:

    • Host web.k8s.local, all paths → Service web
    • TLS using existing Secret web-cert
    • Redirect HTTP to HTTPS

    Answer

    apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web
  namespace: prod
spec:
  ingressClassName: cilium
  tls:
  - hosts:
    - web.k8s.local
    secretName: web-cert
  rules:
  - host: web.k8s.local
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web
            port:
              number: 80

    Cilium usually redirects HTTP→HTTPS when tls is set for that host. If HTTP is still served, add:

    metadata:
  annotations:
    ingress.cilium.io/force-https: "true"
    kubectl apply -f web-ingress.yaml
curl -L http://web.k8s.local

    tls.hosts must match rules.host exactly.
