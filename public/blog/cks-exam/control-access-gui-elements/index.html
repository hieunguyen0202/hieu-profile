    Control Access to GUI Elements

    • We should only expose services externally if we really need to.
    • If we need to access some service that is not available to everyone, we can simply use kubectl port-forward or kubectl proxy instead of exposing through a load balancer.

    The Kubernetes Dashboard has many privileges in the cluster and Tesla was hacked in 2018 because of this.

    • It doesn't use RBAC or roles
    • Tesla's Kubernetes was exposed to the Internet, which is not a standard practice.

    Kubectl Proxy and Kubectl Port-Forward

    Proxy

    • Creates a proxy server between localhost and the Kubernetes API server.
    • Uses the connection configured in your kubeconfig and the credentials to communicate with the api server.
    • Allows accessing the Kubernetes API locally with HTTP and without authentication so it's comfortable to develop and debug.

    Port Forward

    • Forwards connections from localhost on a specific port to a pod's port within the cluster.
    • More generic than kubectl proxy.
    • Can be used for TCP protocols and not just HTTP as in the case of kubectl proxy.

    The pod IP is the cluster's internal IP. We have, for example, the Dashboard pod running in the cluster without being exposed externally.

    • If we have the api-server running inside a pod, we can also use port forward.

    Kubernetes Dashboard

    If we want to expose the dashboard to the Internet without using kubectl, we should take certain precautions such as using an Ingress (Nginx) and applying proper security such as authentication using LDAP or some other system.

    We need to pay attention:

    • Only expose to the internet if needed and if protected.
    • Restrict access using RBAC.
    • Enforce security.
    • Change the deployment arguments. Check dashboard arguments.

    If we were to apply this as it is... We don't have an ingress, we don't have valid certificates, we don't have authentication yet. The way it is, it's not secure.
